## 1. 正确性（对照官方语义）

### [critical] v2/v3 的 `filter` JSON 中规范合法列被静默丢弃 → 返回未过滤数据
**文件**：`packages/shared/src/server/repositories/lite-queries.ts:216-222`（generic drop）、`packages/shared/src/server/queries/clickhouse-sql/factory.ts:67`（`if (!col) continue` 静默跳过）、`packages/server/src/shaping/observations-v2.ts:106-126`、`packages/server/src/shaping/scores-v2.ts:34-136`

**问题**：两条静默路径导致规范文档明确列出的 filter 列被丢弃，接口返回 200 + 未过滤的完整数据（比 400 更危险）：

1. `createFilterFromFilterState` 对未在 UI column mapping 中登记的列直接 `continue`（factory.ts:67）：
   - v2/observations 丢失：`statusMessage`、`latency`、`timeToFirstToken`、`tokensPerSecond`、`inputTokens`、`outputTokens`、`totalTokens`、`inputCost`、`outputCost`、`totalCost`、`promptName`、`promptVersion`、`input`、`output`（均为 spec "Available Columns" 明文列出）
   - 例：`?filter=[{"type":"number","column":"latency","operator":">=","value":2.5}]`（spec 官方示例）→ 无任何条件，返回全部观测
2. `liteBuildFilterWhere` 对 traces 表字段（`clickhouseTable !== table`）直接 `return`，且特殊分支只认**无前缀**的 `user_id`/`tags`：
   - v2/observations 丢失：`sessionId`、`traceName`、`tags`/`traceTags`（mapping 里 clickhouseSelect 为 `session_id`/`trace_name`/`tags`，走不到 special-case 也不在白名单表内）
   - v2/scores 丢失：`userId`（mapping `t.user_id`，前缀导致 `field === "user_id"` 分支不命中）、`trace_tags`（`t.tags`）、`traceName`（`t.name`）；另有 `booleanValue`（clickhouseSelect 是一段 SQL 表达式，白名单不识别）；`datasetRunId` 简单参数（`secureScoreFilterOptions` field=`dataset_run_id` 不在 `LITE_FILTER_COLUMNS.scores`）同样被丢

**实证**（tsx 直连 `createFilterFromFilterState` + `liteBuildFilterWhere`）：4 个条件（tags/sessionId/traceName/name）编译结果仅为 `name = @str0`；scores 侧 userId/trace_tags/name 三条件同样只剩 `name = @str0`。

**建议修复**：二选一（推荐后者）——
- A. 在 `createFilterFromFilterState`/`liteBuildFilterWhere` 中对"列合法但 lite 无法执行"的过滤抛 `InvalidRequestError`（→400，与上游"未知列 400"一致），至少不静默；
- B. 补齐执行：observations 的 `sessionId`/`tags`/`traceName` 用与 `user_id` 相同的 EXISTS 子查询；scores 的 `userId`/`trace_tags` 拆前缀后走既有 special-case；`datasetRunId` 在 lite 无数据 → 显式返回空集（与 v3 `experimentId` 的处理一致）。并为两类路径补测试。

### [major] v3/scores 声明了 `userId`/`traceTags` 参数但静默忽略，与注释意图矛盾
**文件**：`packages/shared/src/features/scores/interfaces/api/v3/endpoints.ts:75-82`（注释 "Deferred params (always → 400…)"）、`packages/server/src/routes/scores-v3.ts:88-139`（解析后既无 400 校验也不传入查询）

**问题**：官方 spec v3 无 `userId`/`traceTags` 参数（官方对未知参数宽容忽略，与本实现行为一致，但注释明确写"always → 400"）。当前行为=静默忽略，且与同一文件 `.strict()`（其余未知参数 400）的策略不一致。使用者 `?userId=x` 会得到未过滤结果且无任何提示。

**建议**：按注释意图在 route 层对非空 `userId`/`traceTags` 返回 400（`?userId=` 空串已在 transform 归一为 undefined，不会误伤模板系统）；或删掉注释改为"兼容忽略"并写明理由。补一条测试。

### [major] session 级 score 无法写入：`trace_id NOT NULL` + 写路径不写 `session_id`/`metadata`
**文件**：`packages/shared/src/server/adapters/sqlite-telemetry-adapter.ts:248`（`trace_id TEXT NOT NULL`）、`packages/shared/src/server/ingestion/processEventBatchLite.ts:183-206`（score row 无 session_id/metadata 列、`trace_id: body.traceId ?? null`）、`packages/server/src/routes/scores.ts:353-381`（fallback insert 同样缺列）

**问题**：v1 POST `/scores`（spec："supports trace, observation, **session**, and dataset run scores"）与 ingestion 对 session score（有 `sessionId`、无 `traceId`）：
- 主路径：`INSERT OR REPLACE` 撞 `NOT NULL constraint failed: scores.trace_id` → 被 processEventBatchLite:379 的 catch 吞掉 → **返回 200 `{id}` 但数据未落库（静默丢失）**；
- fallback 路径（CATEGORICAL/TEXT/CORRECTION session score）：`db.insert` 未包 try/catch → 直接 **500**。
- 顺带：两处写路径都不写 `metadata`/`session_id` → 本次新增的 v3 `details.metadata`、`sessionId` 过滤、subject `kind=session` 全部只能读到空/永远为空。

**实证**：SQLite 直插 `trace_id=NULL` 复现 `NOT NULL constraint failed`。

**建议**：建表/迁移将 `trace_id` 改为可空（`TEXT`，不 NOT NULL），写路径补 `session_id`、`metadata`（`body.metadata` 序列化 JSON）两列；fallback insert 补列并加 try/catch→500 语义明确。补一条"POST session score → GET v3 可见且 subject.kind=session"测试。

### [minor] CORRECTION score 值丢失
**文件**：`packages/server/src/shaping/scores-v3.ts:241-247, 260-263`、`packages/shared/src/server/ingestion/processEventBatchLite.ts:171-182`

**问题**：CORRECTION 的修正文本（string）写在 `value` 列（REAL），`string_value` 为空；读取侧 `rowToScoreDomain` 的 `longStringValue` 取自 `string_value` → 恒为 `""`，`polymorphicValueForV3` 对 CORRECTION 返回空串；且 `Number(row.value)` 对非数字文本产生 NaN（shapeRow 会把它原样带出，APIScoreSchemaV3 CORRECTION 分支 value:string 校验失败 → 行被静默丢弃）。v3/v2 均无法正确回读 CORRECTION。

**建议**：写路径把 CORRECTION 文本落到 `string_value`（或新增 `long_string_value` 列并写它），读取侧对应取列；`value` 列对 CORRECTION 写 0 占位（与 CATEGORICAL/TEXT 一致）。

### [minor] v2/observations `parseIoAsJson=true` 应按 spec 返回 400
**文件**：`packages/server/src/routes/observations-v2.ts:129`、`packages/server/src/schemas/observations-v2.ts:12-13`

spec 原文："**Deprecated.** Setting this to `true` will return a 400 error."。本实现"kept working"（true 时按 JSON 解析）。宽松实现不破坏 CLI，但偏离 spec 的显式契约。建议按 spec 对 `true` 返回 400（false/缺省放行）。

### [minor] v3 分页行被 schema 校验静默丢弃
**文件**：`packages/server/src/routes/scores-v3.ts:144`（`filterAndValidateV3GetScoreList(data)` 未传 onParseError）、`packages/shared/src/features/scores/interfaces/api/v3/validation.ts:10-22`

单行转换/校验失败时该行静默消失，可能出现 `hasMore=true` 但本页不足 limit 条。上游同样静默但带 logger；建议至少传 onParseError 记日志（上游行为），避免排障无头绪。

### [minor] v2/scores 的 `environment` 与 trace 过滤组合时被二次应用
**文件**：`packages/server/src/shaping/scores-v2.ts:181-192`

`if (props.environment && tracesFilter.length > 0)` 会把 environment 追加到 traces 子查询——当 score.environment ≠ trace.environment 时，结果比官方（environment 只过滤 scores 表）更窄。仅 `environment` + `userId`/`traceTags` 组合时触发。建议去掉该追加（scores 表的 environment 过滤已由 scoresFilter 覆盖）。

### [minor] v3 `limit>100`、400 响应体形状与官方不一致
**文件**：`packages/server/src/routes/scores-v3.ts:91-94`、`scores-v2.ts:49-52`

官方 400 响应体为 `{message}`；本实现返回 `{message: "Invalid request data", error: issues}`。CLI/SDK 通常只读 `message`，风险低；若追求严格对齐可在 onError 统一收敛。另：v3 的 400 文案 "Invalid cursor format" 与官方（无固定文案）可接受。

## 3. 安全

- **SQL 注入面（总体可控，PASS）**：
  - `json_extract` 键：factory.ts `toSqliteJsonPath` 单引号转义 `''` ✓；metrics-v2-filters.ts `jsonPath` 用 `."…"` + `\"` 转义（SQLite JSON path 合法）✓；
  - 列白名单 `LITE_FILTER_COLUMNS`（lite-queries.ts:68-108）+ `json_extract` 基列正则 `^json_extract\(\s*([A-Za-z_][A-Za-z0-9_]*)\s*,` 只放行标识符 ✓；
  - 所有值走绑定参数 ✓；v3 `buildValueFilterClause` 列名硬编码 ✓；metrics 所有 SQL 片段来自硬编码 catalog ✓。
- **[suggestion] `BooleanFilter`/`NullFilter` 桩实现返回 `1=1`**（clickhouse-filter.ts:203-240）：`apply()`/`toSql()` 是 no-op。当前仅 `liteBuildFilterWhere` 以 raw 字段消费（安全），但任何未来 ClickHouse 路径复用这两个类会静默吞过滤条件。建议要么实现真实 SQL，要么在 apply() 里 throw。
- **[suggestion] `liteBuildFilterWhere` 的 number/datetime/boolean 分支把 `operator` 直接拼进 SQL**（lite-queries.ts:250-271）：当前所有生产方（zod singleFilter、route schema、v2 固定 operator 列表）均已校验，无注入路径；建议加一层 `allowedOps` 白名单防御纵深（防未来调用方绕过校验）。
- **[minor] tag LIKE 匹配不转义 `"`**（lite-queries.ts:168, 190, 198；`escapeLike` 只处理 `\%_`）：tag 含 `"` 时匹配失真（假阴性，非注入）。建议在 `%"…"%` 拼接前替换 `"`。

## 4. 健壮性

- **PASS**：cursor 语义正确（`(timestamp,id) < (last,lastId)` 与 `ORDER BY ts DESC, id DESC` 一致；SQLite row-value 比较已实证；同 ts 多行翻页测试覆盖）；v3 limit>100→400、末页 cursor=null、非法 cursor→400（含 transform 抛错 try/catch 包裹，routes/scores-v3.ts:107-115）；v2/observations limit max 1000、非法 cursor→400；`?valueMin=` 空串归一（避免 0 误伤）；`fromTimestamp`/`toTimestamp` 空串归一。

- **[minor] 测试环境缺口**：新增 `packages/shared/src/server/repositories/lite-queries.test.ts` 在 shared 包环境（无 server 包 global-setup 的 env 补齐）下 0 用例执行（collection 阶段 ZodError）；`factory.test.ts` 12 用例通过。建议给 shared vitest 补 lite env setup 或将该测试并入 server 包。
- **[minor] 测试覆盖缺口**（server 176 测试通过但未覆盖）：filter JSON 静默丢弃列（两端点）、session score 写入、v3 `userId` 行为、CORRECTION 回读。上述 [critical]/[major] 修复后应逐一补测。
- **[suggestion] metrics 高基数维度 400 文案**（shaping/metrics-v2.ts:160-163）提示"require both config.row_limit and orderBy…"是 v3 top-N 策略的描述，v2 语义为"仅可过滤不可分组"，文案会误导；改直白说明。
