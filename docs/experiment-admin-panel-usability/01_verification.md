# 验证报告 1：后台管理员面板可用性——事故发现与根因调查

## 总体评估

**PARTIAL**

报告能够支持三个范围受限的结论：当前 Errors UI 没有环境筛选、错误详情选择不进入 URL、所测单条 trace 可以从错误详情下钻并看到父子链。它也如实披露了非独立浏览器执行、单一样本根因链和空态未覆盖等限制。

但本轮不能完整验证原假设。所谓“4 个主要动作”只覆盖 Dashboard 到 full trace 的线性点击路径，没有包含一次实际的时间收窄，也不可能包含环境收窄；接口表中的 `TTFB` 若来自服务日志 `durationMs`，指标名称不成立；原始 DOM、URL、网络日志或截图没有随报告落盘，独立审计与复现能力有限。因此方向性发现可信，整体成功标准尚未通过。

## 逐维度评估

### 数据完整性: PARTIAL

已采集动作路径、部分 URL 状态、错误/trace 计数、响应体字节数，以及一个错误详情到完整 trace 的链路。报告也明确记录了未覆盖项，没有把有数据路径冒充空态验证。

主要缺口如下：

- 没有执行并记录一次时间范围切换后的 URL、计数变化、请求参数及后退/刷新恢复；“存在时间选项”和“默认 7d”不等于验证了“按时间缩小范围”。
- 环境控件缺失有 DOM 摘要和实现可交叉确认，但报告没有记录样本数据中实际有哪些环境、同一 fingerprint 是否跨环境，因而不能量化该缺口在本数据集上的影响规模。
- 根因链只检查了一个 `provider_or_stream_failure` 样本。该数据足以证明“这个样本可追溯”，不足以证明不同错误类型、缺失 parent、孤儿 observation 等情况均可追溯。报告已正确承认这一点。
- 没有覆盖“无数据”“兼容接口过滤”“请求失败”三类状态。由于这是规划中的明确成功标准，本轮不能评价该标准是否满足。
- 接口计量缺少请求 URL、采集工具/字段、时间戳、日志原文或导出文件。报告中的 DOM、动作和接口值均是二手摘要，无法从报告目录内追溯到原始证据。
- 响应字节表只证明列出的请求小于 1 MiB；在没有完整请求清单或网络导出的情况下，不能证明页面加载期间的所有相关接口都被覆盖。

### 方法正确性: PARTIAL

只读操作、固定项目、桌面视口和不触碰 Gateway 的控制方向与研究问题匹配；以真实数据走调查路径也适合发现可用性死路。

但证据采集由主任务执行，报告者只整理摘要。这不是自动使结论无效，尤其报告已主动披露偏差；不过它削弱了 verifier 对操作顺序、遗漏请求、选择性记录和 UI 状态的独立判断。报告者没有独立复现，也没有收到可审计的原始证据附件，因此“独立整理”不能等同于“独立实验”。

“4 个主要动作”的计数规则对纯线性下钻是透明且基本公平的：Dashboard 是给定起点，随后四次点击分别进入 Errors、选择 fingerprint、选择错误和打开完整 trace。但它只支持“4 次点击到 full trace”这一窄结论。原假设同时要求按时间和环境缩小范围；当前四步中没有时间操作，且环境操作不可用。若“缩小范围”要求管理员主动选择时间与环境，这些动作必须计入，原报告不能据此宣称完整任务在四动作内完成。规划本身也应进一步定义“主要动作”是否包含筛选选择、输入、提交和展开面板，以避免事后口径。

接口时延方法存在指标错误。`packages/server/src/large-response-logger.ts` 的 `durationMs` 从服务端中间件进入前开始，直到响应 body 的计数流 `flush` 时结束；它包含服务端处理与响应流消费时间，不测量客户端从发起请求到收到首字节的网络 TTFB。若表中数值来自该日志，应改称“服务端请求至响应流结束耗时（durationMs）”。若另有浏览器网络计时，则报告必须注明具体字段与采集方法后才能称 TTFB。

### 结论合理性: PARTIAL

以下结论由证据充分支持：当前页面未提供可操作的环境筛选；选中错误未 URL 化；列出的请求响应体均小于 1 MiB；所测样本可以进入完整 trace 并看到一条错误节点链。

将环境筛选缺失列为 P1 是合理的，但理由应限定在预先定义的任务标准：环境收窄是核心任务，而当前 UI 根本无法执行，因此该成功标准被阻断。仅凭“environment textbox 数量为 0”还不能证明本次 fingerprint 确实横跨生产与预发，也不能量化真实事故影响；“会阻止值班管理员分离事故范围”应表述为在多环境数据下的条件性推断，并用至少两个环境的数据补证。

报告没有把单个根因链外推为普遍能力，反而明确限制为一个真实样本，这一处理合理。相应地，结论中“共同提供了可用根因链”也应始终带上“对本样本”限定。

P2 的 error detail URL 化由刷新、后退和交接目标直接支撑。相比之下，“fingerprint 汇总增加 user/session 数”尚缺少任务时间、误判案例、用户需求或对照实验支撑；现有证据只证明汇总层没有该信息，不能证明聚合计数是最佳修复，也不能确定 P2 优先级。它应作为待验证设计假设，而非本轮已证实的修复要求。

空态补测、环境筛选和详情 URL 恢复均可由规划或本轮证据支持。具体实现范围仍需在修复实验中验证参数语义、清空/恢复行为、跨项目隔离和缺失关联数据口径，不能从本轮可用性观察直接推导出完整接口设计。

### 报告质量: PARTIAL

报告结构完整，表格清楚，显式区分事实与推断，并诚实列出方法偏差、首次基础设施阻塞、单样本限制与未覆盖空态。这些做法显著提高了可信度。

扣分点是原始证据不可追溯、`TTFB` 标签可能错误，以及“4 动作完成根因下钻”容易被读成完整原假设已在四动作内完成。最终状态 `DONE_WITH_CONCERNS` 不是 verifier 模板的 PASS/PARTIAL/FAIL 体系，虽不构成数据错误，但不利于跨轮比较；建议同时给出对每项成功标准的通过状态。

## 关键问题

1. **完整任务与四动作结论混淆**：四次点击验证了线性下钻，没有验证主动时间收窄，也没有完成环境收窄。
2. **证据采集与分析分离且无原始附件**：浏览器由主任务操作，报告者只能审阅摘要，无法排除遗漏与选择性记录。
3. **时延指标命名不成立**：服务端 `durationMs` 不是严格网络 TTFB；当前表无法支持客户端首字节性能结论。
4. **环境 P1 的任务阻断成立，但生产影响尚未量化**：缺控件足以判定预设任务失败，跨环境污染的现实程度仍需数据。
5. **根因链外部效度低**：只覆盖一个 fingerprint 的一条 trace，不能推广到全部错误形态。
6. **空态与失败态成功标准未验证**：三类状态的可区分性仍是证据空白。
7. **部分建议超出证据**：user/session 聚合展示及其 P2 优先级尚未通过实验比较或管理员需求证据确认。

## 改进建议

1. 下一轮预先固定动作计数协议：一次点击、一次筛选值选择、一次文本提交分别如何计数；同时分别报告“到达 full trace 的点击数”和“完成全部筛选与追溯任务的总动作数”。
2. 实际切换至少两个时间范围，保存每步 URL、请求查询参数、结果计数，并验证刷新、后退、前进和 Clear filters；环境修复后以相同矩阵验证环境参数。
3. 将原始证据落盘到本实验目录，例如带时间戳的动作日志、关键截图/DOM 快照和脱敏的 HAR 或网络导出；每个报告表格行引用证据文件与记录编号。不得包含 API secret 或完整敏感 IO。
4. 将现有时延列改名为与来源一致的 `durationMs`；如确需 TTFB，使用浏览器 PerformanceResourceTiming 或 HAR 的 `wait`/首字节定义，注明工具、字段、缓存状态与重复次数，并与服务端耗时分列。
5. 环境 P1 复测至少准备 production/staging 两个环境，并选择一个跨环境 fingerprint，验证全局计数、fingerprint 计数、分页和 URL 恢复均按环境收窄，同时增加 project isolation 测试。
6. 根因链抽样至少覆盖：有多级 parent、无 parent、parent 缺失/孤儿、不同 observation type、同一 trace 多个错误。逐类记录是否能从错误证据定位到来源，不用单样本比例外推总体。
7. 通过可逆查询条件制造有数据与零结果状态，并用受控失败方式验证请求失败态；兼容过滤空态应单独构造。记录文案、下一步操作和清空/重试是否有效，不创建或删除业务数据。
8. 将 user/session 汇总先列为候选方案。先测管理员判断影响范围所需的额外下钻次数和现有 trace 链接是否足够，再比较“聚合计数”“明确下钻入口”“口径提示”三种方案后决定优先级。
