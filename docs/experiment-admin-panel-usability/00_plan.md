# 后台管理员面板可用性：两轮实验规划

## 研究问题

以负责生产 LLM 可观测性的后台管理员为对象，验证 Lite 面板能否高效完成两类真实任务：

1. 发现近期异常、判断影响范围并追溯到错误源头。
2. 核对用户/会话/评分/观测数据口径，并安全管理项目凭据。

## 成功标准

- 关键任务没有死路：列表、筛选、详情和跨模块下钻形成闭环。
- 时间、环境和对象筛选可发现、可恢复、可清空；显式 Search 不丢弃输入。
- 管理员能区分“没有数据”“被兼容接口过滤”“请求失败”三种状态。
- 常用列表首屏不传输完整 IO；单接口响应超过 1 MiB 必须记录并解释。
- 危险写操作必须二次确认；实验不得创建或删除业务数据。
- 每轮发现的高优先级问题完成修复，并由独立 verifier 审查证据。

## 变量与控制

- **自变量**：筛选能力、默认列、跨模块链接、详情加载策略、空态/提示文案。
- **因变量**：任务完成路径、交互次数、URL 状态、响应字节数、错误/空态可解释性。
- **控制变量**：同一 Default Project、同一本地大数据集、1280×720 左右桌面视口、同一暗色主题、
  不修改 Gateway 模块、不执行真实删除/创建。

## 第 1 轮：事故发现与根因调查

- **假设**：管理员可从 Dashboard 在 4 个主要动作内进入近期错误，按时间和环境缩小范围，
  查看影响 trace，并沿父节点/完整 trace 找到错误源头。
- **场景**：Dashboard → Errors → fingerprint → error detail → full trace。
- **指标**：动作路径、时间/环境筛选可用性、受影响范围信息、URL 可恢复性、列表响应字节数、
  根因链是否完整、页面文案是否能指导下一步。
- **修复优先级**：P0 数据错误/权限风险；P1 阻断调查或口径不可信；P2 摩擦与信息密度。

## 第 2 轮：运营治理与数据可信度

- **假设**：管理员可在指定时间/环境内核对用户和会话使用量，从 score/observation 回到归属对象，
  并理解 API key 的生命周期与风险。
- **场景**：Users ↔ Traces；Sessions → trace → observation；Scores/Observations → 来源；Settings。
- **指标**：时间窗口一致性、环境筛选、跨模块参数传递、未关联数据解释、空态指导、危险操作保护、
  响应字节数与首屏任务密度。
- **第 2 轮必须吸收第 1 轮 verifier 反馈。**

## 视觉与交互方向

- 沿用现有 Spectra token：品牌蓝仅用于导航/选择，危险红仅用于错误与撤销风险。
- Inter 用于控制与正文，JetBrains Mono 用于 ID、时间和数值；不增加装饰性字体。
- 页面结构保持“范围 → 筛选 → 数据 → 调查详情”；本轮的签名元素是可恢复的调查上下文，
  不是新的视觉装饰。
- 对窄视口使用明确的常用筛选与更多筛选层级，避免任意换行形成半截工具栏。

## 约束

- 不触碰 Gateway 功能。
- 保留用户未提交的 `packages/cli/package.json` 修改。
- `/api/public/*` 保持 Langfuse SDK 向后兼容，所有查询维持 `projectId` 隔离。
- 不读取或输出 API secret，不创建/删除额外凭据或业务数据。
