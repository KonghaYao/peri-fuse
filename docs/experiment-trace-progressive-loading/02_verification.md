# 验证报告 2：Trace 渐进加载实现后复测

## 总体评估

**PARTIAL**

固定 trace/session 的体积结论可信；缓存混比与 session 缺测已纠正。但首屏总传输、默认契约和
日志隐私仍缺完整证据，不能宣称全部成功标准通过。

## 逐维度评估

### 数据完整性: PARTIAL

trace 指标齐全；同一 23433 进程补得默认 session 565,012,529 B，单样本足以确认该固定 JSON
的体积数量级，不足以外推。未保存脚本、响应头、脱敏日志或浏览器 waterfall，原始证据可追溯性弱。

### 方法正确性: PARTIAL

新端口和 PID 避免复用 23432 旧进程，但仍是 dirty 开发进程，缺启动命令及实际 patch 标识。
MISS/HIT/SKIP 已分开，session 只比 bytes、不比耗时，正确回应上一轮；样本少且顺序固定，报告
也未建立延迟因果。

### 结论合理性: PARTIAL

`1-(678+96872)/191169335=99.94897194%`，基线为轻量的 1959.706 倍；99.94897%/约
1,960 倍口径正确。选中详情后的 99.45078% 与 session 的 99.99924% 也正确。

“首屏约 98 kB”仅合计 shell+summary，漏计页面初始 trace IO 请求，且无 waterfall；应改称
“两个响应合计”。“完整 IO 仅限选中项”应限定为 observation IO。默认 trace 的 24 B 增量恰等于
新增 `,\"observationCount\":2032`，只能证明完整 observations 仍返回，不能证明 schema 不变；
未跑 SDK 契约，兼容性证据不足。

### 报告质量: PARTIAL

算术、缓存口径与局限清楚，但“首屏”结论和无 waterfall 的限制冲突，且缺原始附件。

## 关键问题与改进建议

1. 用 waterfall 统计包含 trace IO 的首屏请求，并确认不自动翻页/预取详情。
2. 对 trace/session 默认响应做字段快照或 SDK 契约测试。
3. 日志源码固定键、去 query 且不读取鉴权/正文，单测覆盖 query 脱敏，设计证据较强；但现场
   warning 和敏感词扫描无附件。保存脱敏样本并增加鉴权/正文哨兵断言。

## 上一轮反馈的处理情况

缓存混比已修复，session 基线已补；旧端口风险仅部分修复。dirty 版本、浏览器首屏、完整兼容与
日志可追溯性仍未解决。
