# 验证报告 1：Trace 渐进加载基线与最小复现

## 总体评估

**PARTIAL**

报告可靠地证明了一个范围有限但重要的事实：在实验时点、目标 project 和目标 trace 上，
默认 trace 响应稳定为 `191,169,311` bytes，而三种轻量请求分别为 `649`、`684,862`
和 `18,376` bytes。两次重复的响应体积完全一致，足以支撑这个固定数据快照上的数量级结论，
也足以说明渐进加载有很大的 payload 优化空间。

但本轮不能把耗时均值当成公平的方案对比，也没有证明 **observation IO 单独** 是 191 MB
响应的主要来源。现有对照证明的是“嵌入完整 observations（其中包含 IO）”主导响应体积。
此外，复用来源未固定的开发进程、dirty worktree 和认证 key 写入使结果不能作为相对 Git HEAD
或实现前版本的严格基线。原计划要求的 session 基线也未采集。

## 逐维度评估

### 数据完整性: PARTIAL

- 四个已测请求组都记录了 status、bytes、TTFB、total 和 `X-Cache`，表格与原始 TSV
  相互一致；每组两次响应的 bytes 也完全一致，没有未解释的体积异常。
- 对“这个 trace 在这个实验时点的响应有多大”而言，`n=2` 已足以确认数量级，因为响应是
  确定性 JSON 序列化，且两次值逐字节数相同。它不能建立跨 trace、跨数据变更或并发条件下的
  响应体积分布；因此 `191,169,311` bytes 只能作为单个重型 trace 的案例数据，不能外推为
  所有 trace 的典型体积。
- 对耗时而言，`n=2` 不足。轻量组的 run 1 是 `MISS`、run 2 是 `HIT`，两者并非同一总体；
  默认组两次都是 `SKIP`。报告第 98 行虽然正确声明样本量限制，但第 101--106 行仍对混合的
  冷热样本计算均值、中位数和标准差。这些统计量不代表稳定的冷请求或热请求分布。
- 原计划第 1 轮明确要求真实请求完整 trace/session；报告第 155--156 行没有测 session，且称
  “本轮任务没有要求 session endpoint”，与 `00_plan.md` 的轮次定义不一致。
- 原始数值嵌入报告，可进行算术复核；但没有保存完整测量脚本、请求响应头样本、服务启动命令
  或运行源码标识。第 163--179 行只展示一个请求的测量结构，不足以精确重放四组请求及其顺序。

### 方法正确性: PARTIAL

- 使用同一数据库、projectId、traceId、端口，并在每组前等待超过 2 秒 TTL，是合理的最小复现
  设计。响应正文写 `/dev/null`、不打印密钥，也符合安全边界。
- 缓存状态不对称是耗时比较的主要混杂变量。默认响应超过 32 MiB 因而 `SKIP`，每次都会执行
  查询、整形和传输；轻量响应第二次直接 `HIT`。因此第 101--106 行的组间均值不能用于量化
  轻量协议相对默认协议的耗时改善。第 125--128 行只比较 run 1 的冷请求更合理，但每组只有一次
  MISS，且固定请求顺序没有控制 SQLite/OS page cache、JIT、GC、热重载和背景负载。
- dirty worktree 是高影响扰动。报告记录了 Git HEAD，但服务复用了既有 PID，未证明该 PID 的
  启动时点、启动命令、实际载入文件版本或是否在测量期间热重载。相关 trace、observations、
  session 路由正在修改，因此结果只能描述该未知进程当时的行为，不能归因到 HEAD，也不能作为
  干净的“实现前”基线。当前源码 diff 还能看到 v2 observation projection 正在变化，这正是本轮
  轻量请求的关键自变量之一。
- 三次 `activate` 会修改认证表并可能裁剪旧 key，违反“同一数据库完全不变”的严格控制条件。
  不过这些写入发生在测量前，且不改变目标 trace/observations 内容，因此对响应 bytes 的风险低；
  除非与请求重叠造成 SQLite 锁竞争，否则对已记录耗时的直接影响也可能较小。报告未记录写入结束
  到首个样本之间的静置时间或锁状态，所以仍不能完全排除耗时扰动。
- 请求顺序固定而未交错或随机化，会把随时间变化的服务热度系统性地绑定到具体请求组。

### 结论合理性: PARTIAL

- “该目标 trace 的默认响应约 191 MB，而轻量首批响应低四到五个数量级”有直接数据支持，
  结论可信度高。
- “完整 observations 嵌入是响应膨胀的主导因素”基本成立。默认请求与
  `fields=core,io,scores,metrics` 保留了 trace IO、scores 和 metrics，主要差别是后者不嵌入
  observations；两者相差约 `190,484,449` bytes（99.64%）。这为把 observations 从首屏响应中
  移除提供了强证据。
- 但“observation IO 是主要来源”尚未证明。trace 路由在请求 `observations` 时会把 observation
  IO 一并读出和返回，实验没有对相同数量、相同非 IO 字段的 observations 做 `with IO` 与
  `without IO` 对照。`v2 core 50` 同时改变了 endpoint、分页数量（50 vs 2,032）和字段集合，
  不能隔离 IO 的贡献。其他 observation 字段的序列化体积也没有单独测量。
- 本轮没有采集查询计划、SQLite 读取字节、CPU/序列化耗时或网络发送耗时，因此也没有证明
  **磁盘/SQLite IO 是耗时的主要来源**。`TTFB` 是数据库查询、JSON 解析/整形、序列化、事件循环
  阻塞和中间件成本的合计；`total - TTFB` 只能粗略反映本地传输尾段，不能做内部归因。
- 报告提出的“core → observation core 分页 → 单条 IO”是由体积证据支持的合理设计方向，
  但尚未用浏览器瀑布证明首屏可用时间，也未证明前端不会自动遍历全部分页或预取全部 IO。
- 默认 API 兼容性、大响应 warning、project isolation 和 session 渐进加载都未在本轮验证；
  它们应保留为后续成功标准，不能由本报告宣称完成。

### 报告质量: PASS

- 结构完整，明确列出环境、方法、原始数据、分析、异常、复现结构和后续建议。
- 对 cache 不对称、样本量、固定顺序、dirty worktree 和认证副作用均主动披露，事实与推断总体
  区分良好。
- 主要措辞瑕疵是第 118 行把“observation IO/完整 observations”并列成一个结论，容易让读者
  误以为 IO 已被单独归因；应收窄为“包含 IO 的完整 observations”。第 134 行“后端现有能力”
  也应限定为实验时点的 dirty-worktree 服务能力，而不是已确认属于 HEAD 的既有能力。

## 关键问题

1. **耗时样本不可合并**：轻量请求的 MISS/HIT 与默认请求的 SKIP 不可直接平均比较，且冷请求
   每组只有一个样本。
2. **IO 因果未隔离**：实验只隔离了是否嵌入完整 observations，没有隔离 observation IO 与
   observation 其他字段，更没有隔离 SQLite IO、序列化和传输耗时。
3. **运行版本不可追溯**：dirty worktree 上复用既有开发进程，PID 和 Git HEAD 不能证明实际
   加载的源码版本；本轮不是严格的实现前基线。
4. **认证写入扰动数据库**：三次 activate 创建/裁剪 key。对 bytes 的影响低，但削弱了数据库
   不变和耗时控制条件。
5. **计划覆盖不完整**：缺失 session 基线；浏览器首屏、大响应 warning 和兼容性属于后续轮次，
   本轮没有证据。
6. **可复现材料不完整**：缺少完整四组测量脚本、服务启动与源码标识、机器负载/热重载状态。

## 改进建议

1. 实现稳定后使用干净、固定 commit（或记录完整 patch hash）启动全新服务；记录启动命令、PID、
   服务启动时间和构建/源码 revision，并在测量期间禁用热重载与并行开发修改。
2. 冷、热性能分别报告。冷请求对每组至少采集 5--10 次同状态样本，每次确保 TTL 过期或显式清空
   测试缓存；热请求单独采集 HIT。将请求组交错或随机化，并记录背景负载。默认 SKIP 只能与轻量
   MISS 的冷路径比较，不能与 HIT 比较。
3. 为验证 IO 体积贡献，在相同 endpoint、相同 observation 集合、相同分页大小和相同非 IO 字段下，
   对比 `fields=core` 与 `fields=core,io`；最好覆盖多个分页，并同时用数据库只读统计
   `SUM(LENGTH(input) + LENGTH(output))` 交叉核对。只有该对照才能把 IO 从其他字段中隔离出来。
4. 若要证明“IO 是耗时主要来源”，增加分段观测：SQLite query duration、读取/返回行字节、整形与
   JSON 序列化 duration、TTFB 和 total；必要时检查 query plan。不能只凭 payload 大小推断数据库 IO。
5. 在正式计时前一次性准备并复用测量 key，等待写事务完全结束；记录 activate 与首个样本的间隔。
   不需要为了本实验清理旧 key，避免额外数据库写入。
6. 补齐相同 project 下的重型 session 基线，并在下一轮保存浏览器 network waterfall，确认首屏没有
   默认完整 trace、自动拉完所有 observation 页或批量预取 IO。
7. 保存不含凭据的完整测量脚本和原始 TSV/响应头元数据；明确报告中的每个结论对应哪一组原始数据。
